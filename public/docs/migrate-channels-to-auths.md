Это руководство поможет перевести интеграции, которые создают, получают, обновляют или удаляют каналы, а также слушают связанные с ними вебхуки.

> **Warning:** **Каналы** API v1 будут отключены. Точная дата будет объявлена позднее в этом году. После отключения API Каналов v1 перестанет работать полностью — перейдите на [каналы API v2](/v2/auths).

## Что меняется

Сущность та же — каналы. Меняется API:

| Что | API v1 | API v2 |
| --- | ------ | ------ |
| Базовый URL | `https://api.pact.im/p1/...` | `https://api.pact.im/api/p2/...` |
| Вебхуки каналов | Данные с `entity: "channel"`, `type: "qr_code"` и похожими полями — см. [Вебхуки v1](/v1/webhooks) | Единый формат с `"type": "auth"` и `"event": "create" \| "update" \| "delete"` — см. [События каналов](/v2/webhooks/auth-events) |
| Способ подтверждения канала | Методы `request_code` / `confirm` и данные из вебхуков (QR и т.п.) | [Подтвердить канал](/v2/auths/confirm-auth) (QR, код или OAuth) и при необходимости [Включить канал](/v2/auths/enable-auth) |
| API-методы каналов | `/p1/companies/:company_id/channels/...` | `/api/p2/companies/:company_id/auths/...` — см. [Каналы](/v2/auths) |

Аутентификация по-прежнему выполняется вашим приватным API-токеном. В v2 обычно передаётся параметр `private_api_token` в query-строке или в теле запроса — см. [Аутентификация](/v2/authentication-v1).

## Соответствие эндпоинтов

| Действие | API v1 (Channels) | API v2 (Auths) |
| ------ | ----------------- | -------------- |
| Список | `GET /p1/companies/:company_id/channels` | [Каналы компании](/v2/auths/get-company-auths) — `GET /api/p2/companies/:company_id/auths` |
| Создание / подключение | `POST /p1/companies/:company_id/channels` | [Создать канал](/v2/auths/create-auth) — `POST /api/p2/companies/:company_id/auths` |
| Подтверждение (код / включение) | `POST .../channels/:id/request_code`, `POST .../channels/:id/confirm` | [Подтвердить канал](/v2/auths/confirm-auth) и [Включить канал](/v2/auths/enable-auth) |
| Отключение / пауза | — | [Отключить канал](/v2/auths/disable-auth) |
| Повторное включение | — | [Включить канал](/v2/auths/enable-auth) |
| Удаление | `DELETE /p1/companies/:company_id/channels/:id` | [Удалить канал](/v2/auths/delete-auth) |
| Список по нескольким компаниям | — | [Каналы (несколько компаний)](/v2/auths/get-auths) |

Параметры создания, специфичные для провайдера (токен, номер телефона, период синхронизации и так далее), описаны в разделе [Создать канал](/v2/auths/create-auth).

## Сценарии подтверждения (QR, код, OAuth)

В v1 подтверждение было разбросано по созданию канала, методам `request_code` и `confirm`, а также по данным вебхуков (например, QR-коды).

В v2:

1. Выполните [Создать канал](/v2/auths/create-auth) для нужного провайдера.
2. Пройдите сценарий, описанный в разделе [Подтвердить канал](/v2/auths/confirm-auth):
   - **QR** — WhatsApp, Telegram Personal, MAX (`qr` в ответе и в вебхуках)
   - **Код** — WhatsApp / Telegram Personal, если передан `phone_number`
   - **OAuth** — Facebook, VK, Instagram Business, WhatsApp Business, Avito (`oauth_provider_url`)
3. Используйте [Включить канал](/v2/auths/enable-auth), когда провайдер требует код подтверждения (например, сценарий с кодом у Telegram Personal).

## Миграция вебхуков

События жизненного цикла каналов в v1 присылали данные с `entity: "channel"`, `type: "qr_code"` и похожими структурами, описанными в разделе [Вебхуки v1](/v1/webhooks).

В v2 приходит единый формат с `"type": "auth"` и `"event": "create" | "update" | "delete"`. Полные примеры и их значения описаны в разделе [События каналов](/v2/webhooks/auth-events).

| Ситуация | Событие канала в v2 |
| --------- | ------------- |
| Канал создан | `event: create` |
| Подключён / готов к работе | `event: update` со `state: enabled` |
| Отключён | `event: update` со `state: disabled` |
| Удалён | `event: delete` |
| Обновление QR, список страниц, прогресс OAuth | `event: update` (см. примеры в разделе событий каналов) |

### Чек-лист для обработчиков вебхуков

1. Зарегистрируйте или обновите URL вебхука компании через [Вебхуки компании](/v2/company-webhooks) (если вы ещё не получаете события v2).
2. Научитесь принимать формат v2: `event`, `type`, `object`.
3. Когда `type === "auth"`, читайте состояние провайдера из `object` (а также `pages` / `qr` / `oauth_provider_url`, если они присутствуют).
4. Перестаньте опираться в новой логике на поля, существовавшие только в v1: `channel_id`, `channel_type`, `entity: "channel"`.
5. Сохраняйте обработчики v1 только пока на старом API остаётся трафик; запланируйте их отключение после переключения.

## Рекомендуемые шаги миграции

1. **Изучите обзор каналов в v2** — [Каналы](/v2/auths) и [объект канала](/v2/auths#auth-object) (`auth` в API).
2. **Сопоставьте вызовы** — замените каждый используемый эндпоинт Channels на соответствующий метод Auths из таблицы выше.
3. **Обновите создание и подтверждение** — следуйте разделам [Создать канал](/v2/auths/create-auth) и [Подтвердить канал](/v2/auths/confirm-auth) для каждого поддерживаемого провайдера.
4. **Переключите вебхуки** — реализуйте обработку [Событий каналов](/v2/webhooks/auth-events); проверьте создание / подключение / отключение / удаление на тестовой компании.
5. **Проведите проверку** — получите список каналов, создайте один тестовый канал, пройдите подтверждение, убедитесь в приходе вебхуков, затем удалите или отключите тестовый канал.
6. **Переключитесь** — направьте продакшен-трафик на v2; уберите использование Channels v1, когда будете готовы.
